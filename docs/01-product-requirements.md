# 产品需求

## 1. 产品目标

让项目所有者把含有未来时间信息的内容交给 QQ Bot，系统能够可靠地识别事件或任务、结合项目内已有安排和可追溯知识提出建议，在确认后保存内部日程，并按时通过 QQ 主动提醒。

首版验证的不是“全自动管理时间”，而是下面这条闭环是否值得信任：

```text
提交信息 → 得到正确理解 → 检索相关背景 → 得到可用建议
→ 确认后进入内部日程 → 到期主动提醒
```

## 2. 目标用户

首版及当前可预见范围只服务项目所有者本人。系统只接受 `.env` 中配置的 QQ 用户身份，其他用户即使能够联系 Bot 也不得读取数据、创建日程或调用 AI。

不设计注册、邀请、租户、组织、角色或公开发布能力。

## 3. 权限原则

- 只有用户直接对 Bot 发出的消息具有命令权限。
- 邮件、转发聊天、附件、图片、网页和 RAG 片段只提供事实，不得直接触发日程变更或消息发送。
- 创建、修改或删除内部日程默认需要用户确认。
- 任何自动化例外必须是用户明确启用、范围有限且可随时撤销的规则。

## 4. MVP 范围

### P0：形成闭环

1. QQ 用户直接输入自然语言。
2. QQ 转发的纯文本消息。
3. Outlook/Hotmail/Microsoft 365 邮件只读同步。
4. 识别固定事件、截止任务、模糊安排请求。
5. 读取项目内部日程的已有事件、任务和忙闲状态。
6. 生成一个主建议和最多两个备选时间。
7. 在 QQ 中确认、修改或取消建议。
8. 用户确认后创建内部日程条目和提醒计划。
9. 保存来源、提取结果、确认记录和执行结果。
10. 到期通过 QQ 主动提醒，并支持完成、推迟和取消。
11. 对历史邮件、QQ 转发内容和用户笔记建立可追溯 RAG 索引。
12. 回答和排程建议引用检索来源；检索结果不能直接触发操作。

### P1：明显增强体验

- QQ 图片、截图和合并转发记录。
- PDF 和邮件附件。
- QQ 邮箱 IMAP 连接器。
- Gmail 连接器。
- 多邮箱。
- 每日摘要、冲突提醒和授权失效提醒。
- 标准 `.ics` 会议邀请的确定性解析。

### P2：长期个人能力

- 工作平台原生连接器。
- 任务系统双向同步。
- 自动移动既有日程。
- 长期习惯学习和工作负载分析。
- 在不引入其他用户账号的前提下辅助多人会议时间信息整理。

## 5. 明确不做

首版不做以下能力：

- 不读取用户未明确授权的账号或数据。
- 不使用邮箱密码；QQ 邮箱仅允许使用授权码。
- 不允许外部内容直接发号施令。
- 不自动删除或移动用户既有内部日程。
- 不替用户发送邮件或 QQ 消息。
- 不提供其他用户账号、团队空间、注册邀请或组织管理。
- 不承诺识别所有附件格式。
- 不将 Task 简单转换成截止日当天的 Event。
- 不以 LLM 输出直接驱动日程变更或 QQ 消息发送。

## 6. 核心用户故事与验收

### PR-01 连接 Outlook

用户可以通过 Microsoft OAuth 连接个人或组织邮箱。

验收条件：

- 使用 Authorization Code Flow、PKCE、`state` 和 `nonce`。
- 请求 `openid profile email offline_access User.Read Mail.Read`。
- 系统不接触 Microsoft 账号密码。
- refresh token 加密保存，断开连接后删除。
- 授权失败、拒绝和过期有明确提示。

### PR-02 从消息识别固定事件

输入“周三 15:00 和王总过方案”时，系统提取标题、时间、参与人和来源。

验收条件：

- 相对日期基于消息原始时间和用户时区解释。
- 缺少持续时间时使用可配置默认值，并明确展示该假设。
- 创建前展示确认卡片。

### PR-03 从邮件识别任务

邮件包含“请于周五前提交报价单”时，系统生成 Task，而不是直接占用截止日。

验收条件：

- 保存邮件来源引用。
- 提取截止时间并标记预计耗时是否缺失。
- 缺少预计耗时时只追问必要问题或使用显式默认值。

### PR-04 生成排程建议

用户要求“下周找两小时写报告”时，系统根据内部日程提出可用时间。

验收条件：

- 不与不可移动事件冲突。
- 遵守用户工作时间、提前量和时区。
- 提供建议理由及冲突说明。
- 建议本身不修改日程，也不发送主动提醒。

### PR-05 确认后写入内部日程

用户明确确认某个 Proposal 后，系统创建对应内部日程条目和提醒计划。

验收条件：

- 确认必须绑定具体 Proposal 版本，过期版本不能执行。
- 操作具备幂等键，重复请求不会创建重复事件。
- 执行结果保存日程条目 ID、提醒计划和审计记录。

### PR-06 可追溯与撤销

用户可以查看“为什么创建了这个日程”，并撤销 Agent 创建的内部日程。

验收条件：

- 显示原始来源、结构化提取、建议和确认记录。
- 撤销只影响 Agent 自己创建且仍可安全撤销的资源。
- 撤销本身也需要确认并写入审计日志。

### PR-07 主动提醒

系统在内部日程的提醒时间到达后，通过 QQ Bot 主动通知项目所有者。

验收条件：

- 提醒任务采用持久化调度，进程重启不会永久丢失。
- 同一提醒实例具有幂等键，重试不会造成重复轰炸。
- 发送失败按 QQ 平台限制退避重试，超过上限进入死信并告警。
- 提醒消息支持完成、推迟和查看来源；状态变更必须绑定具体日程版本。

### PR-08 RAG 检索增强

系统可以从已保存的邮件、QQ 转发内容和用户笔记中检索与当前问题或日程相关的背景。

验收条件：

- 每个检索片段保留来源、原始时间和内容版本。
- 默认使用语义、关键词和元数据过滤的混合检索。
- 没有足够证据时明确说明，不能凭相似文本补造事实。
- RAG 索引不是日程、任务、确认状态或提醒状态的事实源。
- 删除或更新来源后，对应片段和向量可重建或删除。

## 7. 非功能需求

| 编号 | 要求 |
|---|---|
| NFR-01 | 所有公网流量使用 HTTPS；应用只监听回环地址 |
| NFR-02 | 凭据和 token 不出现在日志、错误页、聊天回复和数据库明文字段中 |
| NFR-03 | 接收入口快速响应，耗时处理异步执行 |
| NFR-04 | 同一外部消息重复投递不会生成重复 Inbox Item 或 Action |
| NFR-05 | 所有时间以带时区的时间保存，禁止无时区时间进入领域层 |
| NFR-06 | Provider 故障不得破坏领域数据；支持重试和死信处理 |
| NFR-07 | LLM 输出必须经过结构校验、业务校验和确认策略 |
| NFR-08 | 用户可断开连接并删除凭据及派生数据 |
| NFR-09 | 内部日程写入和 QQ 主动消息必须可审计；日程写入默认可撤销 |
| NFR-10 | 提醒任务至少一次执行，借助幂等键实现用户可感知的恰好一次效果 |
| NFR-11 | RAG 回答必须返回来源引用，并记录索引采用的模型和维度版本 |

## 8. 成功指标

北极星指标：每周经用户接受、写入内部日程且按时提醒的有效安排数。

辅助指标：

- 建议确认率。
- 用户修改建议时间的比例。
- 从提交到安排完成的交互轮数。
- 错误创建、重复创建和撤销比例。
- 邮件同步成功率和授权失效率。
- 用户持续向 Bot 提交时间信息的周留存。
